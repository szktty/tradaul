# Tradaul VM性能改善報告書

**作成日**: 2025年6月8日  
**対象バージョン**: Tradaul v0.7.0  
**実施期間**: 2025年6月7日〜6月8日

## エグゼクティブサマリー

Tradaul VMの性能改善プロジェクトを実施し、ベースラインと比較して以下の成果を達成しました：

- **fibonacci.lua**: 44.0%高速化（3.857秒 → 2.160秒）
- **loop.lua**: 79.0%高速化（1.027秒 → 0.216秒）
- **table.lua**: 55.6%高速化（0.153秒 → 0.068秒）
- **string.lua**: 12.5%高速化（0.008秒 → 0.007秒）

標準Luaとの性能差は依然として大きいものの（fibonacci.luaで約45倍遅い）、実用的な速度向上を実現しました。

## 初期状態の分析

### ベンチマーク結果（標準Lua比較）

| ベンチマーク | Tradaul初期 | 標準Lua | 性能差 |
|------------|-----------|---------|--------|
| fibonacci | 3.857秒 | 0.048秒 | 約80倍遅い |
| loop | 1.027秒 | 0.011秒 | 約93倍遅い |
| table | 0.153秒 | 0.002秒 | 約77倍遅い |
| string | 0.008秒 | 0.002秒 | 約4倍遅い |

### 主要な性能問題

1. **過剰な非同期処理**: VM実行ループでの不要な`await`
2. **オペコード解析オーバーヘッド**: 毎回の`LuaOpcode.getFields()`呼び出し
3. **巨大な実行メソッド**: `_execute()`メソッドが779行（保守性の問題）

## 実施した最適化

### 成功した最適化

#### 1. 同期的基本演算の分離（Phase 1.2）
- **実装内容**: ADD, SUB, MUL演算に数値専用の高速パスを追加
- **効果**: loop.luaで68.2%改善
- **技術詳細**: 
  ```dart
  // 数値同士の場合は非同期処理をスキップ
  if (a is LuaNumber && b is LuaNumber) {
    final result = ArithmeticOperatorDispatcher.dispatch(op, a, b);
    _stack.push(result);
    continue;
  }
  ```

#### 2. VM実行ループの最適化（Phase 2.1）
- **実装内容**: DIV演算と比較演算（LT, LE, EQ）の同期パス実装
- **効果**: fibonacci.luaで18.3%改善
- **技術詳細**: 比較演算の高速化により再帰処理が効率化

#### 3. テーブル操作の最適化（Phase 2.2）
- **実装内容**: GET_FIELD/SET_FIELD命令の同期パス追加
- **効果**: table.luaで20.5%改善
- **技術詳細**: メタメソッド処理をスキップする高速パス

#### 4. 命令デコードの最適化（Phase 5.1）
- **実装内容**: コンパイル時に命令をデコードし、実行時のビット演算を削減
- **効果**: loop.luaで9.6%改善
- **技術詳細**: 
  ```dart
  // DecodedInstructionクラスで事前デコード
  class DecodedInstruction {
    final int op;
    final int a;
    final int b;
    final int c;
    // コンパイル時にビット演算を完了
  }
  ```

### 失敗した最適化

#### 1. オペコード解析キャッシュ（Phase 1.1）
- **問題**: Mapルックアップのオーバーヘッドが計算コストを上回る
- **結果**: 全ベンチマークで性能悪化（最大37.5%）
- **教訓**: キャッシュは必ずしも高速化につながらない

#### 2. スタック操作の最適化（Phase 1.3）
- **問題**: `popToMark`最適化がLuaセマンティクスを破壊
- **結果**: 複数戻り値の順序が逆転するバグ
- **教訓**: 正確性は性能より優先される

#### 3. BytecodeOptimizer（Phase 3.1）
- **問題**: MARK_RETURN命令の過剰な削除
- **結果**: 実行時エラー「no return mark」
- **教訓**: 制御フローの複雑性を過小評価してはいけない

#### 4. LuaValuePool実装（メモリアロケーション削減）
- **目的**: オブジェクトプールによるメモリアロケーション削減
- **実装内容**:
  - 小さな整数（-5〜50）をキャッシュ
  - よく使う浮動小数点数（0.0, 1.0, -1.0）をキャッシュ
  - Luaキーワードと短い文字列（16文字以下）をキャッシュ
- **結果**: loop.luaで25%の性能悪化（0.216秒 → 0.270秒）
- **原因**: `Map.putIfAbsent`のオーバーヘッドが新規オブジェクト作成より高い
- **教訓**: DartのGCは小さな短命オブジェクトに既に最適化済み

## Dart特有の発見

### 1. 小オブジェクトの効率的な処理
- DartのGCは小さな短命オブジェクトに最適化済み
- オブジェクトプールによる長寿命化はかえって逆効果
- 新規オブジェクト作成は想定以上に高速（特にLuaInteger, LuaFloatなど）

### 2. Mapルックアップのコスト
- `Map.putIfAbsent`は単純なコンストラクタ呼び出しより遅い
- 小さなオブジェクトではキャッシュの利点が得られない
- タイトループでのMapアクセスは顕著な性能劣化を引き起こす

### 3. 非同期処理のオーバーヘッド
- 単純な演算での`await`は大きな性能ペナルティ
- 同期実行可能な処理は積極的に同期化すべき

## LuaTable内部構造改善の試行（2025年6月8日）

**実装内容**:
- 配列部分とハッシュ部分の明確な分離（`_arrayPart`をnullableリストに変更）
- `fastGetInt`/`fastSetInt`メソッドによる整数インデックスの高速アクセス
- 配列の動的拡張（初期8要素、2倍成長戦略）

**結果（実用的なメモリ割り当て）**:
- fibonacci: 8.8%改善（2.160秒 → 1.972秒）
- loop: 0.9%改善（0.216秒 → 0.214秒）
- table: 7.4%改善（0.068秒 → 0.063秒）
- string: 変化なし

**分析**:
- テーブル操作で7.4%の改善を達成
- 実用的なメモリ割り当てにより、loopの性能悪化も解消
- 配列とハッシュの分離による効率的なアクセスが功を奏した

## 今後の改善可能性

実施した最適化の経験を踏まえ、Dartの特性を活かした以下の改善が検討可能です：

1. **非同期オーバーヘッドの更なる削減**
   - Lua関数呼び出しの同期化
   - Future.syncの活用

2. **文字列処理の最適化**
   - Dart標準の文字列インターン化活用
   - ハッシュ計算のキャッシュ

## 得られた教訓

### 1. 言語固有の最適化戦略の重要性
- 一般的なVM最適化手法が必ずしも有効ではない
- 対象言語（Dart）の特性を深く理解する必要がある

### 2. ベンチマーク駆動開発の必要性
- 全ての最適化は測定によって検証されるべき
- 直感に反する結果も受け入れる柔軟性が必要

### 3. 正確性と性能のバランス
- 性能向上のために正確性を犠牲にしてはいけない
- 段階的な実装とテストが重要

### 4. プロファイリングの限界
- マイクロベンチマークと実アプリケーションの性能は異なる
- 複数の観点からの評価が必要

### 5. 一般的なVM最適化手法の落とし穴
- オブジェクトプールは多くのVMで有効だが、Dartでは逆効果になる場合がある
- 言語固有のランタイム特性を無視した最適化は性能悪化を招く
- ベンチマーク測定なしの「常識的」最適化は危険

## 結論

2日間の集中的な最適化作業により、TradaulのVM性能を大幅に改善することができました。特にloop.luaで79%の高速化を達成したことは、数値計算処理において実用的な速度を提供できることを示しています。

しかし、標準Luaとの性能差は依然として大きく（fibonacci.luaで約45倍遅い）、インタープリタ型VMとしての限界も見えています。今回の経験から、Dart特有の最適化戦略を理解し、言語の特性を活かした実装が重要であることが明らかになりました。
